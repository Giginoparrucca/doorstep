Round 61 — Puglia SPOT Online XML export
Goal and target user
A Puglia struttura ricettiva (B&B, affittacamere, small hotel) files its monthly tourist-flow statistics through SPOT Online on the DMS Puglia portal. SPOT Online accepts an XML file generated by the gestionale, in a format of its own. Today WelcomeBnB only gives these hosts a "manual-entry reference CSV" (Round 58), so they retype every guest by hand.
This Round generates the real SPOT Online XML file from submitted check-ins, so the host downloads one file, uploads it with "Carica movimentazione" and clicks "Invia movimentazione". It also remembers, per property, whether the property uses SPOT Easy or SPOT Online, so the tile and labels stop showing the wrong service.
No portal submission. Upload stays manual: SPOT is reachable only after a SPID/CIE/CNS/eIDAS login on dms.puglia.it. Never automate that login and never store digital-identity credentials.
Zero-impact rule: SPOT Easy (`ps` TXT), Alloggiati, ROSS1000, Umbria, Trento, summary CSV and PayTourist outputs stay byte-identical. Properties outside Puglia see no change.
Out of scope: SPOT Completo (desktop app), ROSS1000 web-service sending, any API to DMS/ARET, qualitative ISTAT fields we don't collect (trip purpose, transport, booking channel, education).

Format summary (from the spec — the spec wins if this summary disagrees)

* XML 1.0, UTF-8. Root `<movimenti vendor="WelcomeBnB">`, then one `<movimento>` per day. Any file name without special characters.
* `<movimento data="YYYY-MM-DD" type="…">`:
   * `MP` (movement): at least one `<arrivi>` or `<partenze>`, plus `<datistruttura>`.
   * `NM` (open, no arrivals/departures): no `<arrivi>`/`<partenze>`.
   * `EC` (closed): no arrivals/departures, and nobody present the night before.
   * Spec section 2.2.2.3 says `<movimento>` always has `<datistruttura>`; the startup examples show empty `NM`/`EC` elements. Resolve with the XSD; until then, emit `<datistruttura>` on every non-startup day (the portal UI also asks for capacity on "Nessuna movimentazione" days) and record the choice.
* `<datistruttura>`: `<cameredisponibili>`, `<postilettodisponibili>`, `<camereoccupate>`. occupied ≤ rooms ≤ beds; all zero on `EC` days.
* `<arrivi>` holds one `<arrivo>` per single guest (16), capofamiglia (17) or capogruppo (18). Same codes as Alloggiati. Members (our `member` 19 and `group_member` 20) are not arrivals: they go inside the head's `<componenti><componente>`. A single guest must not have `<componenti>`; a head must have it.
* Required per `<arrivo>`: `codiceclientesr`, `sesso` (M/F), `cittadinanza` (Alloggiati 9-digit state code), `paeseresidenza` or `comuneresidenza` (Alloggiati codes), `occupazionepostoletto` (si/no), `dayuse` (si/no), `tipologiaalloggiato`, `eta` (age at check-in).
* Required per `<componente>`: `codiceclientesr`, `sesso`, `cittadinanza`, residence, `occupazionepostoletto`, `eta`. Members inherit dayuse and the qualitative fields from the head.
* `codiceclientesr`: unique and stable per guest in our system, no personal data (no codice fiscale, no names). Departures are filed by this code.
* `<partenze>` lists `<codiceclientesr>` of guests leaving that day. A head's code departs the whole group/family. A member leaving early is listed alone. If only the head leaves early, the head's code carries `partenzacapogrupposeparata="SI"` and the remaining members are later listed individually.
* Strict sequence: a day is accepted only if the previous day was already processed, and a gap stops processing at the missing date. The very first file a structure ever sends starts with a "startup" `<movimento>` dated the day before its first day, listing guests present that night as arrivals (only required fields), or `<movimento type="NM" …/>` if nobody was present.
* Optional qualitative fields (`caratteristicheviaggio`, `duratasoggiorno`, `mezzotrasportoarrivo`, `mezzotrasportomovimento`, `motivazioniviaggio`, `titolostudio`): omit them. We don't collect them and must not invent values such as "non specificato".

Phase 2 — SPOT Online XML serializer

* New format `spot_online` in `lib/regional-exports.js`, used when region = Puglia and `regional_service = 'spot_online'`. Replaces the summary CSV for those properties. SPOT Easy keeps format `ps` unchanged.
* Reuse the existing helpers: `scope` (property, submitted, not deleted, not test), `country`, `comune` (strict; no citizenship→residence or birthplace→residence fallback), `idFor` for `codiceclientesr` (stable, non-identifying, ≤20 chars; reuse keeps one code per guest across all regional files). Check whether the XSD limits its length or charset once obtained.
* Residence: `residence_country` required; Italian residents need a verified comune code (`comuneresidenza`); foreign residents use `paeseresidenza`. Missing or ambiguous residence is a blocking validation error pointing at the guest, as for ROSS1000.
* Age: whole years at arrival date from `date_of_birth`; validate DOB ≤ arrival.
* `dayuse`: `no` unless arrival = departure (cannot happen today; validation requires departure > arrival). Keep the code path explicit and tested.
* `occupazionepostoletto`: comes from the review step (Phase 3), never guessed in the serializer. Missing value = validation error.
* Group structure: members must have exactly one head with the same `booking_code` and arrival date (existing `group` validation). Members nested under the head; heads sorted before singles only if the spec requires an order (it does not appear to; keep a deterministic order: by arrival, then `idFor`).
* Departures: head code when the whole group leaves together; individual codes for early-leaving members; `partenzacapogrupposeparata="SI"` when the head leaves before members, then members individually on their own day.
* Period: every date from start to end appears exactly once (`MP`, `NM` or `EC` from the daily review); no gaps, no future days (reuse Round 58 rules). Carry-over guests (arrived before start) appear only in `<partenze>` and in occupancy, never as new arrivals.
* Optional startup block (Phase 3 toggle): `<movimento>` for start − 1 listing guests present that night (arrival < start ≤ departure) as arrivals with required fields only, or `type="NM"` if none.
* Output: `spot_online_<start>_<end>.xml`, `application/xml;charset=utf-8`.
* XSD: try to obtain `movimentogiornaliero-0.6.xsd` / `datatype-0.6.xsd` from the public DMS document library. If found, commit them under `docs/spot/` with source URL and date, and validate every golden file against them in the test (e.g. with `xmllint --schema` or a pure-JS validator already in devDependencies — don't add a heavy dependency without noting it). If not found, validate against the spec rules above, write the exact request text for ARET into the CHANGELOG as an owner action for Daniele, and label the export "built to official spec v1.0; awaiting XSD/portal confirmation" in the source register (not in the host UI).
* Golden files (AGENTS.md rule 7), synthetic data only, under `scripts/golden/synthetic/`: `spot-online-fixtures.json` and `spot-online-expected.xml` covering: single Italian resident; foreign family with members (one child sharing a bed → `no`); group with an early-leaving member; head leaving before members; carry-over arrival before start; an `NM` day; an `EC` day; two rooms occupied on the same night (Round 60 rooms); startup block on and off. Byte-for-byte comparison plus an independent parse check (well-formed XML, per-day sequence, every departure code previously arrived in the file or carried over, occupied ≤ rooms ≤ beds, counts of arrivals/departures per day match the fixture).
* Regression: existing regional, Alloggiati, PayTourist golden tests must stay byte-identical. Full regression.

Phase 3 — Review dialog, host guidance and guide

* When the saved service is SPOT Online, the regional review dialog shows:
   * The daily opening/availability grid as today (Round 58 + Round 60 room prefills), including the unassigned-room flags.
   * A per-guest "Occupa un posto letto" column, default sì, which the host switches to no for a child sharing a bed. Show the age next to it so under-3s are easy to spot. Not saved to the database (download-only, like other review edits), unless a later Round decides otherwise.
   * A "Primo invio a SPOT" checkbox (off by default) that adds the startup block, with a one-line explanation.
   * Start date guidance: "Start from the first day SPOT shows as not yet transmitted. SPOT rejects a day if the previous one wasn't sent."
   * A warning when any carry-over guest's arrival falls before the selected start: their departure is filed by our guest code, so SPOT must already know that code. If the host entered those guests by hand in SPOT, the upload will flag them: either start the file on a day with nobody present, or update the codes with SPOT's "Aggiornamento codici clienti".
   * A completeness reminder: the file must include every guest at the property; stays not checked in through WelcomeBnB make it wrong.
* After download: "Upload it on dms.puglia.it → SPOT → Carica movimentazione, fix any rows SPOT marks in red, then press Invia movimentazione. Deadline: the 10th of next month." Downloading never changes any filing status.
